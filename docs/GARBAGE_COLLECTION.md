# Garbage collection

## Назначение и запуск

GC удаляет недостижимые manifests и Blob в LocalStorage и S3 по одному алгоритму.
Он не очищает uploads, SQLite, каталоги репозиториев и неизвестные файлы/ключи.
Удаление старых тегов — отдельная задача.

- Cron: воскресенье, `01:00`, часовой пояс `TZ`.
- Вручную: `cr garbage storage`.
- Один запуск: максимум **10 минут**, включая ожидание блокировки. HTTP-запуск
  дополнительно ограничен context запроса; успешный ответ `200` означает завершение.
- Grace period: **24 часа**, константа `gcRetention`, не настройка YAML.

После удаления тега данные не обязательно исчезают при следующем GC: другой тег,
index или свежий untagged manifest могут сохранять их достижимыми.

## Алгоритм

1. Собрать полный inventory manifests, тегов и Blob. LocalStorage использует
   обход каталогов; S3 — рекурсивный listing только настроенных prefixes.
2. Построить корни: все теги и все manifests возрастом до 24 часов включительно.
   Свежий manifest без тега тоже защищает зависимости — это важно для push,
   когда дочерний manifest уже записан, а index или тег ещё нет.
3. Обойти граф. Поддерживаются OCI image manifest/index и Docker schema 2
   manifest/manifest list, вложенные indexes и поле `subject`. Каждый посещённый
   manifest проверяется по SHA-256 содержимого. Ссылки на config/layers должны
   иметь корректный SHA-256 digest и существовать в inventory Blob.
4. Если обход завершился успешно, выбрать недостижимые объекты **старше** 24 часов.
   Возраст LocalStorage — `mtime`; S3 — `LastModified`. Свежие Blob сохраняются
   независимо от наличия manifest.
5. Удалять manifests, затем Blob. Если удаление завершилось ошибкой, вернуть её;
   уже выполненные удаления не откатываются. При ошибке удаления manifest этап
   Blob пропускается; при ошибке удаления Blob оставшиеся Blob также сохраняются.

Данные Blob при GC не скачиваются и не хешируются: проверяется наличие, а не
целостность их содержимого. Metadata хранятся в памяти; размер inventory растёт
пропорционально числу объектов. Глубина графа ограничена 128 переходами.

## Безопасность при ошибках

Ошибка listing/чтения, неверный digest тега, повреждённый посещаемый manifest,
отсутствующий дочерний manifest или Blob, неизвестный `mediaType`, цикл, слишком
глубокий граф или неизвестный возраст объекта останавливают GC **до удаления**.
Старые недостижимые manifests не разбираются: они являются кандидатами на удаление.

Объекты с именами вне схемы хранения сохраняются. Локальные symlinks в manifests
и blobs запрещены: обнаружение ссылки отменяет запуск. Необычный файл тега,
manifest или Blob также вызывает ошибку.

Сквозная отмена использует `context.Context`. Проверки происходят при обходе,
чтении и удалении; context не может принудительно прервать уже начатый системный
вызов чтения/удаления локального файла.

## Одновременная работа

`maintenanceGate` даёт GC эксклюзивный доступ внутри **одного экземпляра storage**.
Запись manifests, изменение тегов/пространств/репозиториев и финальная публикация
Blob ждут завершения GC. Эти операции между собой остаются параллельными.
Загрузка временных chunks и чтение Blob не блокируются этой защитой.

Это не транзакция всего push: HEAD, публикация Blob и отправка manifest — разные
HTTP-запросы. Grace period защищает обычную новую загрузку, но не гарантирует
безопасность push длительностью более 24 часов или повторного использования
старого недостижимого Blob между HEAD и отправкой manifest. Для таких сценариев
нужно окно обслуживания без push либо отдельный механизм leases/pinning.

Другие процессы, другие экземпляры storage и внешние изменения файлов/bucket
не синхронизируются. Несколько серверов на общем хранилище требуют распределённой
координации; до её реализации GC следует запускать в окне обслуживания.

## Реализация и проверка

- `src/storage/gc.go` — общий mark-and-sweep, retention, проверки и статистика.
- `src/storage/gc_backends.go` — адаптеры Local/S3 и timeout запуска.
- `src/storage/maintenance.go` — отменяемая блокировка обслуживания.
- `src/storage/gc_test.go` — общий контракт backend, повреждение ссылок,
  вложенный граф, grace period, ошибки и отмена блокировки.

Логи содержат `task=garbage_collection`, размеры inventory и достижимого графа,
`candidates`, `deleted`. Ошибка удаления логируется с ключом объекта и возвращается
вызывающему коду; cron фиксирует итоговую ошибку задания.

```bash
cd src
go test ./...
go vet ./...
go test -race ./...
```

S3-сценарии требуют тестовый endpoint и `CR_RUN_S3_TESTS=1`; иначе они пропускаются.
Настройка описана в [S3](S3.md). Тесты используют изолированные buckets.
