# Единый контракт загрузки Blob

LocalStorage и S3 используют общую логику в `storage/blob_upload.go`.
Различается ввод-вывод: локальный файл и JSON рядом с ним либо объекты S3.
Конфигурация backend не изменяет правила работы клиента.

## Состояния

| Фаза | Значение | PATCH | PUT |
|---|---|---|---|
| `uploading` | Подтверждённый offset, финализация не началась | Разрешён с правильным offset | Допускается финальное тело |
| `finalizing` | Финальное тело и ожидаемый digest зафиксированы | HTTP 409 | Только пустое тело и тот же digest |
| `ready` | SHA-256 проверен, публикацию можно повторить | HTTP 409 | Только пустое тело и тот же digest |

После успешной публикации сессия удаляется. GET статуса тогда возвращает 404.
Если очистка после публикации не удалась, остаётся `ready`: завершение можно
повторить с пустым телом. В обоих случаях успешный PUT возвращает **201**.

## HTTP

Базовый путь: `/v2/<namespace>/<image>/blobs/uploads/`.

| Запрос | Результат |
|---|---|
| POST базового пути | 202; Location, UUID и начальный offset |
| GET `<UUID>` | 204; текущие offset и фаза |
| PATCH `<UUID>` | 204; очередная часть записана |
| PUT `<UUID>?digest=sha256:…` | 201; Blob опубликован |
| DELETE `<UUID>` | 204; сессия отменена, повторная отмена допустима |

Для управления сессией, включая GET статуса, требуются права **push** на репозиторий.

Заголовки ответа GET:

- `Docker-Upload-UUID`: идентификатор сессии;
- `Location`: URL этой сессии;
- `Range`: `0-<последний байт>`; для пустой сессии `0-0`;
- `X-Upload-Offset`: точное количество подтверждённых байт, в том числе `0`;
- `X-Upload-State`: фаза;
- `X-Upload-Digest`: ожидаемый digest при финализации, не утверждение о проверке SHA-256.

PATCH требует `Content-Range: <start>-<end>` и точного соответствия длины тела.
`start` равен offset из GET статуса. Неполное или избыточное тело отклоняется.
При неверном offset ответ 416 содержит текущие `Range` и `X-Upload-Offset`.
Ошибочный offset не изменяет загрузку.

Общий лимит — 10 000 непустых чанков, включая непустое тело финального PUT.
Пустой PUT не увеличивает счётчик и разрешён при достижении лимита.
Дополнительные ограничения одного S3-запроса описаны в [S3](S3.md).

## Восстановление после ошибки

1. Не повторяйте автоматически тот же PATCH или непустой PUT.
2. Получите GET статуса UUID.
3. Если фаза `uploading`, продолжайте с возвращённого offset.
4. Если фаза `finalizing` или `ready`, повторите PUT с **пустым телом**
   и прежним digest. Другой digest отклоняется, но не удаляет эту сессию.
5. Если GET вернул 404 после потерянного ответа PUT, проверьте HEAD Blob по
   ожидаемому digest. Если Blob существует, повторная загрузка не требуется.
   Если его нет, начните новую сессию.

Ошибка до фиксации финального тела оставляет сессию `uploading`.
Ошибка проверки или публикации после фиксации оставляет её замороженной.
Вычисленный SHA-256, не совпавший с ожидаемым, приводит к `ErrDigestMismatch`
и попытке удалить сессию. Ошибка удаления отражается в логе запроса.

Возвращённый storage-методом offset при ошибке нельзя считать подтверждением
отката: запись S3 могла завершиться, а ответ потеряться. GET состояния является
источником истины. Одинаковый API восстановления применяется и к LocalStorage.

## Устойчивость локального состояния

Данные записываются в `TMP_PATH/<UUID>`, состояние — в `<UUID>.json`.
JSON заменяется атомарным Rename небольшого metadata-файла; Blob не копируется.
Данные и metadata синхронизируются перед подтверждением записи. Если процесс
остановился после записи хвоста, но до фиксации JSON, лишний хвост обрезается
до сохранённого offset при следующем чтении состояния.

Старые сессии без JSON мигрируются при первом чтении. Их существующие данные
принимаются как подтверждённые; историческое число чанков восстановить нельзя,
поэтому непустая старая загрузка считается одним чанком.

Это восстановление после остановки процесса, а не обещание транзакционной
устойчивости при отказе диска или отключении питания. Не изменяйте файлы/объекты
uploads вручную. TMP_PATH и BLOBS_PATH локального backend должны находиться
на одной файловой системе для публикации через Rename.

## Блокировки и cleanup

Операции одной сессии сериализуются mutex. Ожидание блокировки отменяется context.
Независимые UUID обслуживаются параллельно. Cleanup не ждёт активную сессию,
а пропускает её. Возраст всех временных данных и состояния проверяется под mutex.
Свежий объект или файл запрещает удаление сессии.

`deleted` — число удалённых сессий, не число файлов/объектов. Существующий cron
запускает очистку ежедневно в 02:00; retention — 24 часа, timeout — 5 минут.
После публикации очистка имеет отдельный context на 30 секунд; её ошибка
не превращает успешно опубликованный Blob в HTTP 500.

Поддерживается один процесс на общее хранилище. GC использует отдельную блокировку
публикации и grace period 24 часа; mutex upload-сессии эту задачу не решает.
Распределённые блокировки и атомарная публикация Blob вместе с manifest остаются
отдельными задачами. Ограничения: [Garbage collection](GARBAGE_COLLECTION.md).

## Проверка

`TestBlobUploadContract` запускает один набор сценариев для обоих backend:
offset, ошибка тела, перезапуск, ошибка проверки/публикации, запрет повторного
тела, cleanup после публикации, отмена ожидания mutex и отмена сессии.
`TestBlobUploadHTTPContract` проверяет одинаковые HTTP-ответы и заголовки.

```bash
cd src
go test ./...
go vet ./...
go test -race ./...
```

Для запуска тех же контрактов на реальном S3 задайте тестовое окружение
по [инструкции](S3.md#проверка). Без него S3-подтесты явно пропускаются.
