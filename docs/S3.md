# Работа с S3

## Подключение

Registry поддерживает локальное хранилище и S3 через `minio-go/v7`.
Bucket создаётся администратором заранее: приложение проверяет его доступность
при запуске, но не создаёт автоматически.

В `src/conf.d/config.yaml` (в Docker — `/etc/conf.d/config.yaml`):

```yaml
server:
  realm: https://registry.example.com
  jwt: replace-with-random-secret-at-least-32-bytes

storage:
  type: s3
  bucket: registry
  prefix: var
  credentials:
    endpoint: s3.example.com:9000
    access_key: replace-with-access-key
    secret_key: replace-with-secret-key
    ssl: true

default_user:
  login: admin
  password: replace-with-strong-password
```

`endpoint` — адрес S3 API без `http://` или `https://`, не адрес console.
Для AWS можно указать `s3.amazonaws.com`; TLS должен быть включён.
Необязательные `bucket` и `prefix` по умолчанию равны `registry` и `var`.
`prefix` задаёт собственное пространство ключей внутри bucket.

Само переключение `type` **не переносит данные** LocalStorage в S3.
Для существующих S3-данных выберите prefix, соответствующий прежним ключам.
Старый backend формировал ключи из локального `DATA_PATH`; новый использует
стабильный prefix, одинаковый для локального запуска и Docker.
Перед сменой prefix сделайте резервную копию и проверьте список объектов.

## Что хранится где

При `prefix: var`:

```text
bucket
└── var/
    ├── blobs/<sha256 без префикса sha256:>
    ├── manifests/<пространство>/<образ>/sha256:<digest>
    ├── manifests/<пространство>/<образ>/tags/<тег>
    └── tmp/uploads/<upload UUID>/
        ├── state.json
        ├── parts/<случайный UUID>
        └── blob
```

Blob, manifests, ссылки тегов и состояние uploads находятся в S3.
На локальном диске остаются SQLite `registry.db`, конфигурация и CLI credentials.
Серверу всё ещё нужен доступный для записи каталог данных для SQLite.
S3 backend не создаёт локальные временные файлы при загрузке или скачивании Blob.

## Загрузка Blob

1. `POST` создаёт `state.json`: список частей, общий размер и состояние проверки.
2. `PATCH` проверяет ожидаемый offset и записывает тело в отдельный S3-объект.
   Состояние изменяется только после успешной записи всего чанка.
   Неполное тело запроса не увеличивает offset.
3. `PUT` дописывает финальное тело, если оно непустое. Части последовательно
   читаются из S3 и через `io.Pipe` собираются во временный объект `blob`.
   В этом же потоке вычисляется SHA-256. Финальное тело и `expected_digest`
   фиксируются одним обновлением state, после чего сессия заморожена.
4. Неверный digest приводит к ошибке и удалению загрузки. Такой Blob не публикуется.
5. При совпадении digest фиксируется `ready_digest`, затем проверенный объект
   публикуется server-side copy/compose в `blobs/<digest>`. Временные объекты удаляются.
6. Если Blob уже существует, проверяются его размер и фактический SHA-256.
   Повреждённый существующий объект не перезаписывается молча.
7. `DELETE` отменяет загрузку и удаляет её временные объекты.

Мелкие Registry PATCH-чанки не являются частями одного S3 multipart upload.
Это позволяет принимать произвольные размеры чанков, в том числе меньше
минимального размера обычной S3 multipart part. Внутри отдельных записей SDK
использует S3 multipart при необходимости, с размером part 16 MiB по умолчанию.
При сборке Blob больше 156,25 GiB размер part увеличивается, чтобы не превышать
10 000 multipart parts; соответственно увеличивается память SDK-буфера.
Один PATCH неизвестной длины ограничен 10 000 parts по 16 MiB.
Ограничение текущей сессии — 10 000 непустых Registry-чанков.

Blob не загружается целиком в память. Память используется для потокового буфера,
буферов multipart SDK и списка частей; её расход зависит и от числа параллельных
uploads. Один SDK PUT выполняется с `NumThreads: 1`.

**Цена подхода:** при завершении части ещё раз читаются из S3 и записываются в S3,
затем выполняется server-side публикация. Это дополнительные S3-запросы,
трафик между registry и S3 и временный объём хранения. Подход выбран для совместимости
с маленькими PATCH-чанками и восстановления после перезапуска, а не для ускорения
относительно LocalStorage.

### Восстановление и конкурентность

Состояние хранится в S3, поэтому другой экземпляр `S3Storage` после остановки
предыдущего может продолжить загрузку с последнего сохранённого offset.

Общие правила offset, восстановления и фаз сессии описаны в
[контракте LocalStorage и S3](BLOB_UPLOADS.md).
После ошибки сначала запрашивайте `GET /v2/<namespace>/<image>/blobs/uploads/<UUID>`.
Ошибка записи состояния в S3 может означать потерянный ответ уже успешной записи.
Возвращённый вместе с ошибкой offset не является подтверждением отката.

В фазах `finalizing` и `ready` завершение повторяется только с прежним digest
и пустым телом PUT. Непустое тело и PATCH явно отклоняются с HTTP 409.
После успешной публикации ошибка cleanup логируется, но PUT возвращает 201;
остатки удаляются планировщиком. Это не протокол exactly-once доставки HTTP-ответа.

Операции одной загрузки сериализуются mutex. Независимые uploads выполняются
параллельно. **Поддерживается один процесс registry на один bucket/prefix.**
Mutex не защищает от одновременной записи несколькими процессами или от ручного
изменения временных объектов. Распределённая блокировка остаётся техдолгом.

## Чтение и обслуживание

- `GET` читает S3-поток напрямую; `http.ServeContent` обеспечивает HTTP Range.
- `HEAD` проверяет наличие Blob без скачивания тела.
- Manifests, OCI indexes, теги, пространства и репозитории обслуживаются через S3.
- Удаление тега не удаляет сразу manifest: он может быть нужен другому OCI index.
- GC обходит весь граф вложенных OCI indexes и проверяет ссылки до начала удаления.
  При повреждённой или отсутствующей ссылке очистка завершается ошибкой.

GC сохраняет свежие объекты 24 часа; свежие untagged manifests защищают свой граф.
Во время GC публикация Blob и изменения manifests/тегов блокируются внутри одного
экземпляра storage. Общей транзакции push и распределённой блокировки нет:
для нескольких процессов, долгого push и повторного использования старых
недостижимых Blob нужно окно обслуживания. Подробности:
[Garbage collection](GARBAGE_COLLECTION.md).

### Очистка uploads

Используется существующая cron-задача: ежедневно в 02:00, срок хранения 24 часа,
timeout одного запуска 5 минут. Часовой пояс берётся из настройки запуска сервера.

Cleanup проверяет возраст объектов и незавершённых multipart uploads каждого UUID.
Если есть свежий объект либо mutex занят, сессия пропускается. UUID повторно
проверяется под mutex. Возвращаемое число `deleted` для S3 — число удалённых сессий,
а не отдельных объектов.

Для orphan multipart uploads необходим корректный `ListMultipartUploads` API.
У RustFS-образа, использованного при проверке, создание upload работало, но список
не возвращал этот upload. Для такой версии provider автоматическая очистка
невидимых orphan uploads невозможна; проверяйте этот сценарий перед эксплуатацией.

Дополнительно настройте bucket lifecycle `AbortIncompleteMultipartUpload`:
это страховка от остановки процесса во время SDK multipart/compose. Не задавайте
обычную expiration-политику на весь bucket: она удалит опубликованные Blob.
При versioning удаление текущих объектов не освобождает предыдущие версии;
отдельно настройте lifecycle noncurrent versions по своей политике хранения.

## Права доступа

Учётной записи registry нужны:

- на bucket: `s3:ListBucket`, `s3:GetBucketLocation`, `s3:ListBucketMultipartUploads`;
- на объекты выбранного prefix: `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`,
  `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts`.

Server-side copy/compose требует доступа на чтение источника и запись назначения.
Для bucket с KMS-шифрованием дополнительно нужны соответствующие KMS-права.
Приложению не нужны права создания или удаления bucket. В тестах они нужны,
поскольку каждый тест создаёт отдельный bucket и удаляет только его.

## Проверка

Обычные проверки из `src`:

```bash
go test ./...
go vet ./...
go test -race ./...
```

Интеграционные тесты требуют отдельного тестового S3 endpoint и credentials
с правами создавать/удалять buckets. Не используйте production credentials.

```bash
export CR_RUN_S3_TESTS=1
export CR_S3_ENDPOINT=127.0.0.1:9000
export CR_S3_ACCESS_KEY=your-test-access-key
export CR_S3_SECRET_KEY=your-test-secret-key
export CR_S3_SSL=false
go test -race ./storage ./handlers -run 'TestS3|TestBlobUploadContract|TestBlobUploadHTTPContract' -v -count=1
```

Проверяются пустые Blob, маленькие чанки, Blob больше 16 MiB, повторная загрузка
одного digest, продолжение новым экземпляром storage, offset, повреждённые объекты,
отмена контекста, mutex, cleanup, manifests, административные операции и HTTP
POST/PATCH/PUT/GET/HEAD/Range/DELETE. Проверка orphan multipart на реальном provider
явно пропускается, если тот не возвращает созданный upload; отдельно этот путь
проверяется локальным тестом S3 API, не требующим внешнего хранилища.
